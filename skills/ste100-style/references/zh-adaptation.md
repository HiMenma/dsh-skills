# 中文技术写作用词与句式对照（STE100 移植）

按 ASD-STE100 的写作纪律改写为中文可执行条目。英文原句与规则号见 `ste100-rules.md`。每节末尾标注来源：`STE`＝ASD-STE100 Issue 9 条文，`STC`＝社区中文移植规范（Simplified Technical Chinese），`仓`＝本仓库既有约定。三个来源不许混为一谈，引用时按标注引。

## 1. 句子层

| 要求 | 中文做法 |
|------|----------|
| 一句一个意思 | 描述句中文 ≤ 40 字，步骤句 ≤ 30 字。两个意思就拆成两句。 |
| 一句只给一个指令 | 步骤句里只出现一个动作。"执行 deploy.sh --all" 之后另起一句讲前提。 |
| 主动语态 | 施事者写在主语位。施事者只能是：我／你／App／管理台／网关／域服务／定时任务／渠道商。 |
| 不写悬空被动 | "该字段已被配置" → "我在 `MappingConfig` 里补了 `.Map`"。 |
| 不用进行时与完成体叠加 | 写"已启用""未启用""将启用"，不写"已经进行了启用的操作"。 |
| 段落短 | 一段 ≤ 6 句。一段只讲一件事，换事换段。 |
| 时态一致 | 同一小节里不要用"了"把已发生和待发生混在一起。 |

来源：句长与段落上限＝`STE` 5.1／6.3／6.6 换算成汉字数（换算系数取自 `STC`）；一句一指令、条件先行＝`STE` 5.2／5.4；主动语态＝`STE` 3.6。**被动句的唯一合法情形**：施动者确实未知，且属描述性文字（`STE` 3.6 原文许可）。这种句子要写明"施动者未知"这件事本身，否则按违规改。

## 2. 义务分档（不许混档）

| 档 | 中文 | 对应英文 | 用于 | 来源 |
|----|------|----------|------|------|
| 硬约束 | 必须／不准 | `MUST`／`DO NOT`（祈使） | 违反即失败：契约必填、启动前置、资金口径 | `STE` 词典 |
| 推荐 | 建议 | STE 里没有这一档 | 不做有代价，但不阻断：加用例、加日志 | `STC`／`仓` |
| 可选 | 可以 | `CAN` | 允许的动作或取值 | `STE` 词典 |

**Issue 9 的实情**：`should` 不批准，被并进 `MUST`；`may` 不批准，改成 `CAN`；`shall` 不批准，改成 `MUST`。也就是说 ASD-STE100 的义务表达比 RFC 2119 更硬，它只有"必须／不准／可以"。本 skill 保留"建议"这一档，因为中文技术文档确实要区分阻断与非阻断。但硬约束一律写"必须"，不许降级成"建议"或"需要"。

**禁用替身词**：`需要`、`有必要`、`得`、`要`、`确保`、`保证`、`尽量`、`酌情`、`必要时`、`原则上`、`一般情况下`、`视情况`、`相应的`、`相关的`、`一定程度`、`基本上`、`可能要`、`应该会`、`待确认`、`有待评估`。

出现这些词时，先判它到底落在哪一档，再改写。判不出档，说明这句话本身还没想清楚。`确保`／`保证` 另有一层问题：它们不写动作。改成那一步具体要做的事（例："确保凭据正确"→"在 `third_party` 表里覆写该通道的凭据，然后重启 transaction 服务"）。

## 3. 用词表：右边换左边

| 用 | 不用 |
|----|------|
| 检查／核对 | 进行检查、做一次核对、予以核查 |
| 删除 | 进行删除操作、执行 delete 的调用 |
| 用 | 通过…的方式、使用…来实现、`utilize` |
| 如果 | 当…时（表条件时；"当…时"只留给时间） |
| 因为 | 由于、基于（表原因时；"基于"只留给比较依据） |
| 空／NULL | 不存在值的情况、空值的情形 |
| 500 字符 | 500 长度、长度限制为 500 的情况 |
| 报错 | 出现异常信息、有错误的表现 |
| 未验证 | 待确认、需要进一步确认（未验证项必须写成可照做的动作） |
| 通道的配置 | 其配置、该配置、相关配置 |
| 这三个字段 | `上述内容`、`以上几点`、`诸如此类` |
| 关闭 | 进行关闭的处理 |
| 现在不做 | 后续优化（要么给出绝对日期，要么写"本期不做"） |

**尾巴词**：句子里出现 `情况`、`问题`、`方面`、`层面`、`进行`、`予以`、`作出`、`相关的`，都是零信息量。删掉后重写。
例：「在幂等方面存在问题」→「重复提交会写两行」。

来源：名词化＝`STE` 3.7；`当…时` 只留给时间、条件用"如果"＝`STE` 词条 WHEN／IF；"因为"改写"由于"＝`STE` due to→BECAUSE OF、since→BECAUSE；同一物只用一个名字＝`STE` 1.11／6.2／9.4；指代必须复写名词＝`STE` GR-3／GR-4（**建议级，不是条文**，故脚本判 WARN）；`基于` 的用法限制＝`仓`。

## 4. 数字、单位、时间

- 时间一律绝对：`2026-10-15 14:20`＋时区（UTC／AUS／服务器 CST 三选一写明）。
- 数字带单位：`500 字符`、`30 秒`、`900 s`。范围两端都带单位：`20 到 200 条`。
- 未实测的数值不写"大约""左右"，写"未测"。
- 版本号、迁移名、错误码原样抄，不意译。

来源：`STC`／`仓`。**ASD-STE100 明确不管计量单位与编号格式**（Issue 9 总引言）。数值与时间的写法要求来自中文移植规范与本仓库的取证习惯，引用时不要写成 STE 条文。

## 5. 结构与列举

- 冒号引导一句完整话，下面每行一个要素；条目句式统一（全祈使句或全名词短语，不混）。
- 层级不超过三层。
- 表格只用于真正的多维对照。字段表、验收用例表可以留；聊天里的结论默认不用表格。
- 列举闭合：写完检查句尾有没有"等"。有就把剩下的补全，或者改成"分两类：A、B"。
- 风险提示按 **条件 → 动作 → 后果** 的顺序写，警示不放进步骤句子中间。
  例：「如果通道 12 未启用，App 仍能选护照，但出款会报 NoRoute。」

来源：列表机制＝`STE` 4.3（引导句以冒号结尾、条目末尾不挂逗号分号、不嵌套、指令与描述不混列）；条件先行＋逗号分隔＝`STE` 5.4；安全文字"先指令或条件、再风险后果"＝`STE` 7.2／7.3；列举闭合＝`STE` GR-6（建议级：不用 `etc.`／`e.g.`／`i.e.`，本 skill 因中文文档实际痛点而判 FAIL）；"聊天默认不用表格"＝`仓`。

## 6. 中英混排

- 代码标识符、API 名、错误码、命令一律保留英文原文。文件名和表列名也一样。用反引号包住，不翻译。
- 整句英文的场合只有两类：对外对接文档、渠道商邮件。这时直接按 STE100 原规则写。句子 ≤ 25 词（程序句 ≤ 20 词），用主动语态，义务只用 must／do not／can，不用进行时和完成时。

来源：`STE` 6.3／5.1／3.2／3.6；词典里 `should`→MUST、`may`→CAN、`shall`→MUST，英文整句不要拿这三个词表义务。

## 7. 反例 → 正例

1. 反：`目前还需要确认一下通道侧是否需要传证件签发日期。`
   正：`未验证：XCurrency 是否强制要求 certificateIssueDate。要确认就去读 beneficiary 字段赋值点。`

2. 反：`对失败原因的长度进行了统一处理，相关表和字段都做了调整。`
   正：`我把父单和子单的 fail_reason 都扩成 varchar(500)。父单不再二次截短。`

3. 反：`系统会自动重试并记录日志，同时也会通知相关人员。`
   正：`系统重试 3 次。每次重试写一条日志。第 3 次仍失败时，系统给运营发站内信。`

4. 反：`当用户提交的资料不完整时会被拒绝。`
   正：`如果资料缺签发日期，域服务就拒绝，并在 response 里返回 issueDateRequired。`

5. 反：`支持身份证、护照等常见证件。`
   正：`支持两类证件：身份证、护照。暂不支持港澳台通行证。`
