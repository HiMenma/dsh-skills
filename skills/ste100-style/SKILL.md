# ASD-STE100 风格约束（中文承载）

## Overview

ASD-STE100 是航空业的可读性规范，本体是英语规则。本 skill 把它的**句子纪律**移植到中文技术写作。语言仍是简体中文。代码标识符、API 名、错误码、命令、文件名保留英文原文。目标只有一个——读者一次读完就能行动，不需要回读。

判断标准不是"写得全不全"，而是"用户能不能照着这句话做决定"。

## 何时启用

| 输出 | 走不走 |
|------|--------|
| 对话里的结论、进展更新、风险与待确认事项 | 走，且是重点 |
| 任何文档（不限目录、不限文件名） | 走。用户手动指定「不用 ste100」时，整份文档不走。 |
| 代码注释、提交信息正文 | 不受本 skill 约束，按仓库既有惯例 |

## 结论契约（对话输出必守）

1. **第一句回答用户问的那一句。** 不要先铺机制、背景、取证过程。
2. **一句一个意思，描述句 ≤ 40 字，步骤句 ≤ 30 字。** 意思多了拆句，不要用「、」串。
3. **主动语态，施事者写明。** 写"我改了 `MappingConfig`"，不写"该字段已配置"。
4. **义务分清档**：硬约束写 `必须`／`不准`，推荐写 `建议`，可选写 `可以`。禁用 `需要确认`、`必要时`、`原则上`、`尽量`、`相应`。注意：ASD-STE100 本身只有"必须／不准／可以"，`should` 被并进 `MUST`；"建议"这一档是本 skill 为中文文档保留的，写它时不许表达硬约束。
5. **事实、推断、未验证三者分开。** 未验证的写 `未验证：<具体项>`，不要混进结论里冒充事实。
6. **列举闭合。** 写全，不用 `等`、`等等`、`其他相关`。
7. **默认用话说完。** 表格只在用户明确要清单时用；自家文档的编号（`D10`、`§9`、决议号）一次都不出现在聊天里。
8. **最多留一个待答问题**，并给出我的推荐与代价。

### 改写前后对照

改写前（机制铺陈、义务不分、开放式列举）：

```text
关于通道适配的问题，目前后端在网关侧和域服务侧都有一定的校验逻辑，
后续可能需要视情况调整相关配置，涉及通道、路由、网络等。
```

改写后（结论先行、三档义务、施事者明确）：

> 结论：App 现在能选护照，但真出款只认身份证。判定在域服务做，不在网关做。你必须先把通道 12 置为启用，否则出款报 NoRoute。建议同步补一条回归用例。未验证：alipay 侧影像是否必填。

## 文档写作规则

写作阶段直接按 `references/zh-adaptation.md` 的条目执行。该文件把 STE100 的写作纪律落到中文，含用词表和反例。规则号与英文原句在 `references/ste100-rules.md`。

三条最容易漏的：

- **指令句与陈述句分开写。** 步骤用祈使句（"执行 `deploy.sh --all`"），解释另起一句。一步一指令，不在一个步骤里塞两个动作。
- **条件写全。** 用"如果 X，就 Y"，不用"当 X 时 Y"（"当…时"只表时间）。条件、动作、后果按这个顺序写。
- **时间用绝对值。** 写 `2026-10-15 部署`，不写 `今天部署`、`最近部署`、`后续部署`。

## 自检流程

产出文档或给出较长结论后：

```bash
node ~/.dsh/skills/ste100-style/scripts/check_style.mjs <文件.md>
# 检查一段即将发出的回复：把文本管道进去
printf '%s\n' "<你的结论>" | node ~/.dsh/skills/ste100-style/scripts/check_style.mjs -
```

1. 跑脚本，读 `FAIL` 列表（`FAIL=0` 才算通过，脚本退出码 1 表示不通过）。
2. 逐条改写，优先改 `ZH-01`（超长句）、`ZH-03`（义务分级）、`ZH-04`（开放式列举）、`ZH-05`（动词名词化）。
3. 复跑。`WARN` 允许保留，但要在回复里点明保留原因（例：`ZH-07` 命中的是引用需求文档的原话）。
4. 脚本只判表面特征，不判"有没有答到问题上"。**先确认回答了用户问的那一句，再谈措辞。**

规则号含义见脚本里的 `RULES` 表。有几条判据不来自 ASD-STE100，引用时别记错来源：`ZH-12`（mermaid）和"聊天默认不用表格"是本仓库既有约定；`ZH-04`（`等`）取自 STE 的建议级 GR-6；`ZH-15`（缩略语给全称）、绝对日期与单位写法来自社区中文移植，STE 总引言明确不管计量单位。逐条来源标注在 `references/zh-adaptation.md` 每节末尾。

判据文档容易自己踩自己的规则。做法：引用的禁用词一律用反引号包住（如 `需要确认`），反例放进代码块，实在没法包的那一行末尾加 `<!-- ste100:allow -->`。豁免只用于这两类，不许拿它压掉真违规。

## 与既有约定的衔接

- 需求/设计文档的结构标准（四模块、接口设计单独拆分、按需求归档）**优先于**本 skill 的措辞规则。本 skill 只管句子怎么写，不管章节怎么排。
- 不用 mermaid：图表改表格／文本／ASCII。
- 用户要求"说简单清楚些"时：**把多层表格改写成大白话分段**，不是再补一轮完整矩阵。这种追问要答得比上一轮更短。
